# Modelo de datos

Fuente ejecutable: infrastructure/database/schema.prisma y doce migraciones. Fechas persistidas con timestamptz; zona de organización para presentación. UUIDs identifican entidades.

## Convenciones de nombres

Entidades y tablas Prisma usan inglés y PascalCase singular (`ServiceAssignment`); campos usan camelCase (`organizationId`, `createdAt`) y enums PascalCase con valores UPPER_SNAKE_CASE. No se traducen identificadores para coincidir con etiquetas españolas de UI. PostgreSQL conserva los identificadores emitidos por Prisma entre comillas; SQL manual debe respetar mayúsculas.

Las FKs usan el nombre de entidad/relación más `Id`; relaciones tenant compuestas incluyen `organizationId`. Prisma nombra sus índices y FKs generados; constraints/triggers manuales usan snake_case descriptivo (`service_interval`, `check_assignment_capacity`). Conservar nombres ya migrados: cualquier cambio requiere migración aditiva/reversible y revisión de consumidores, sin renombrar tablas sólo por estilo.

`Notification` es la entrada IN_APP y su `deliveredAt` indica que ambos transportes locales acabaron. `NotificationDelivery` registra por separado PUSH y EMAIL; un fallo del segundo no obliga a repetir el primero si su entrega quedó persistida. `readAt` existe pero no constituye por sí solo un flujo de marcado como leído. DeviceToken no pertenece a una organización: el mismo usuario puede trabajar en varias y el worker debe comprobar Membership en cada envío futuro. `deviceIdentifier` sólo admite un identificador aleatorio de la instalación, nunca IMEI, ID publicitario ni huella del dispositivo. El campo `token` es secreto operativo; no se expone en API ni logs y su API autenticada permite alta/renovación/revocación sin exponerlo en respuestas. La adquisición cliente, el provider push y la limpieza programada siguen pendientes.

## Integridad

Migración foundation crea el modelo; invariants añade checks de fechas/cantidad, referencias tenant compuestas y unicidad parcial de asignación activa. El trigger bloquea la posición al validar capacidad. La lógica usa transacciones serializables con reintentos de conflictos.

Borradores no son visibles a miembros ordinarios. Los estados terminales no reabren. No se deben borrar confirmaciones históricas para simular un estado actual. Estado y trazabilidad se conservan en tablas separadas.

No se ha implantado una política global de soft delete, retención o eliminación de cuenta. [ACCOUNT_LIFECYCLE.md](ACCOUNT_LIFECYCLE.md) documenta el diseño futuro por entidad, los datos históricos que deben preservarse y las migraciones/pruebas pendientes; no constituye una función disponible.
ChatParticipant.hiddenAt permite retirar una conversación sólo de la lista del participante sin borrar historial ajeno. El envío nuevo recupera visibilidad del destinatario; el reintento idempotente conserva la retirada. Migración 202609300001_chat_hidden.

NoticeRecipient ya está migrado para audiencias ORGANIZATION/USERS; NoticeTarget avanzado, Availability y MembershipJobRole siguen futuros: [DOMAIN_EXTENSIONS.md](DOMAIN_EXTENSIONS.md). Las entidades futuras explican referencias de grupo/rol/servicio, recurrencia e aislamiento previstos. Notice conserva audienceVersion=0 para difusión histórica sin snapshot ficticio; las publicaciones API nuevas usan audienceVersion=1 y NoticeRecipient con FKs compuestas a Notice y Membership del mismo tenant.
