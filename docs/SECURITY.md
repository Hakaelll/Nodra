# Seguridad

Personalización: sólo OWNER/ADMIN con Membership activa puede modificar terminología/acento. La API aplica un enum de tokens, etiquetas de texto acotadas y cuerpo estricto; no acepta HTML, CSS, URLs ni hex libre. Revalida permiso y snapshot esperado dentro de la transacción; auditoría sin etiquetas en metadata. Las Membership propias reciben sólo la configuración necesaria para presentarla. Las etiquetas heredadas se conservan como texto en lecturas/snapshot para corregirlas; los clientes deben renderizarlas como texto, nunca como HTML o CSS.

Dispositivos: la API exige sesión activa y deriva userId de AuthGuard; no admite asignarlo en el cuerpo. Todas las lecturas/revocaciones se limitan a esa cuenta, incluso sin Membership. Devuelve únicamente metadatos. La unicidad del token protege frente a reasignación entre cuentas y las transacciones/constraints evitan registros duplicados. Los tokens permanecen en almacenamiento privado para un adapter futuro; no deben copiarse a logs, respuestas, URLs ni documentación. Registro no prueba entrega push ni propiedad externa del token: los clientes y providers reales aún no están conectados.

Estado: protecciones iniciales implementadas; no es una certificación ni un lanzamiento productivo.

Contraseñas Argon2id con memoria 64 MiB y tres iteraciones. Refresh aleatorio hasheado, familia/rotación/revocación; JWT corto y sesión activa comprobada. La rotación serializable detecta reutilización incluso ante refresh concurrentes y revoca la familia; cambiar contraseña revoca todas las sesiones. Ambos caminos tienen cobertura de integración PostgreSQL para sus efectos sobre los tokens. Invitaciones hasheadas con caducidad, revocación y consumo transaccional. Backend exige Membership activa y permisos por tenant.

Para no omitir el coste de Argon2id cuando el email no existe, el login verifica un hash ficticio con los mismos parámetros. Las cuentas inexistentes, inactivas y con contraseña incorrecta tienen el mismo código/mensaje públicos y no generan sesión, comprobado con PostgreSQL real. El email se normaliza con trim y minúsculas antes de validar y buscar. No se afirma resistencia absoluta a análisis de tiempo; el registro duplicado aún devuelve 409 y revela existencia del correo.

Una matriz HTTP con PostgreSQL real verifica que una cuenta sin Membership en la organización recibe 403 en las 10 rutas de lectura y 16 rutas de escritura bajo /organizations/:org; las mismas rutas sin sesión reciben 401. Los cuerpos y UUID de escritura son válidos, para comprobar la autorización y no sólo la validación. La matriz por sí sola no cubre relaciones internas ni todas las combinaciones de roles.

Una segunda matriz HTTP usa cuatro cuentas con Membership OWNER, ADMIN, COORDINATOR y MEMBER en el mismo tenant. Verifica lectura de servicios/avisos para las cuatro; creación de ambos sólo para los tres roles operativos; y lectura de equipo/ajustes y creación de invitaciones sólo para OWNER/ADMIN. Recuenta las entidades persistidas para asegurar que los 403 no escribieron datos. Es cobertura de esas rutas concretas, no de todas las operaciones ni de transiciones entre roles.

Otra prueba crea servicios, posiciones, asignaciones, roles, grupos, avisos e invitaciones reales en un segundo tenant. El propietario del primero no puede leer ni modificar esas entidades usando sus UUID con la ruta de su organización; se comprueba que permanecen intactas. Una prueba por rol detectó y corrigió que GET /organizations/:org/settings permitía la lectura a COORDINATOR/MEMBER pese a la matriz: ahora exige permiso settings (OWNER/ADMIN). La página web «Configuración» ofrece opciones personales con datos ya autorizados y no usa ese endpoint.

Fastify limita los cuerpos generales a 64 KiB y el JPEG de perfil a 512 KiB, instala Helmet y aplica 120 peticiones/minuto por IP, 10/minuto en rutas de autenticación e invitación sensibles fuera de test. CORS permite WEB_ORIGIN, sin credenciales de navegador directas. BFF web comprueba Origin y utiliza cookies HttpOnly/SameSite Strict. Revisar política de proxy/IP antes de cualquier despliegue.

La API de desarrollo escucha en loopback por defecto. `API_BIND_HOST=0.0.0.0` habilita deliberadamente el acceso LAN para Android debug; no cambia autenticación ni permisos. Exige una red privada de confianza y un firewall limitado a la subred local para el puerto 4000. El cliente Android sólo permite HTTP sin cifrar en debug: las credenciales y tokens cruzan esa red sin cifrar, por lo que esta opción no se debe usar en redes públicas ni en builds de distribución. Producción requiere HTTPS en el punto de entrada.

Logs HTTP redactan Authorization, Cookie y Set-Cookie, y omiten query strings. Errores internos, incluidas excepciones HTTP 5xx, sólo devuelven código, identificador y mensaje genérico. El filtro registra tipo de error y requestId, sin mensaje ni stack; cuatro regresiones comprueban secretos y stack canario, estado 500/503 y validación 400 legible. Esto no certifica todos los logs fuera del filtro. ConsolePush registra únicamente identificadores de destinatario y evento; no registra título, cuerpo ni otros metadatos. No registrar passwords ni tokens en nuevas trazas.

`DeviceToken` tiene rutas autenticadas de registro, renovación, listado y revocación de instalaciones propias. Su `token` es un secreto operativo: nunca incluirlo en respuestas, auditoría o logs. La adquisición del token en los clientes, el provider de push remoto y la purga programada siguen pendientes. `deviceIdentifier` debe ser aleatorio y propio de la instalación, no un identificador de hardware ni de seguimiento.

.env y artefactos locales están ignorados. .env.example sólo contiene valores de desarrollo. La configuración rechaza el secreto marcado development-only en producción, pero eso no garantiza entropía: generar un secreto real fuera del repositorio.

Las subidas implementadas son fotos de perfil y logos de organización. POST /auth/me/avatar exige sesión propia, limita el cuerpo a 512 KiB, decodifica realmente el JPEG con límite de píxeles y dimensiones 512 × 512, y vuelve a codificarlo sin metadatos antes de entregarlo a `ObjectStorageProvider`. El proveedor local predeterminado guarda en `.local/avatars`; escritura mediante fichero temporal y rename, claves limitadas a rutas relativas seguras, y lectura ausente diferenciada de fallo de almacenamiento. El adapter S3 opcional usa claves y tipos validados y un bucket privado; la configuración exige credenciales separadas y HTTPS en producción. GET exige sesión y la clave deriva del id autenticado, no de una ruta del cliente. La carpeta local o el bucket deben mantenerse privados y persistentes. No hay uploads de documentos.

Logos: GET exige Membership activa; POST/DELETE requieren OWNER/ADMIN y vuelven a validar el permiso dentro de la transacción Serializable. La normalización JPEG comparte el límite de tamaño/píxeles de la foto de perfil. Cada subida usa una clave aleatoria bajo `organizations/<org>/logos/`, sin aceptar rutas del cliente ni exponer la clave en la respuesta. Sólo después de confirmar metadatos y auditoría se elimina el logo anterior. Si la transacción falla, se intenta retirar el objeto nuevo. Un proceso terminado entre almacenamiento y transacción, o un fallo de limpieza, puede dejar objetos sin referencia; no se afirma atomicidad distribuida entre PostgreSQL y storage ni existe recolector automático de huérfanos.

Recuperación de contraseña y verificación email usan tokens aleatorios con hash persistido, caducidad y consumo único. El worker conserva el token cifrado sólo mientras debe entregar el correo; lo elimina tras la entrega o descarte. Los enlaces colocan el token en el fragmento URL, fuera de la ruta HTTP, y la web no lo consume automáticamente al abrir la página. La solicitud de recuperación responde de modo genérico para correos existentes o ausentes. El restablecimiento revoca sesiones anteriores. Las pruebas de integración usan PostgreSQL y transporte falso, y una prueba opt-in usa Mailpit real; faltan evaluación de proxy/logs en despliegue y E2E de ambos clientes.

Pendientes: MFA si se decide, implementación de retención/anonimización y eliminación de cuenta, revisión de dependencias, respuesta a incidentes y restores. [ACCOUNT_LIFECYCLE.md](ACCOUNT_LIFECYCLE.md) recoge la estrategia futura y los límites del esquema actual. La aplicación no afirma cumplimiento normativo completo.

La integración del logo también simula una transacción PostgreSQL confirmada cuya respuesta se pierde: la petición falla, pero la lectura posterior conserva el JPEG vigente. Antes de compensar una subida fallida, el servicio bloquea y comprueba la referencia actual; si no puede comprobarla, conserva el archivo. Así la limpieza no da por probado un rollback a partir de un error de transporte.
